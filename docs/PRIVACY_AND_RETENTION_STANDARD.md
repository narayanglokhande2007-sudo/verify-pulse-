# VerifyPulse Privacy and Retention Standard

> **Status:** Draft operational standard — owner approval required before representing it as a contractual policy.
>
> **Scope:** VerifyPulse public scanner, B2B scan API, threat-intelligence pipeline, local feedback controls, and operational telemetry.

## 1. Purpose and design principle

VerifyPulse is designed to detect scam and fraud signals while minimising personal-data handling. The default operating principle is **do not persist raw customer scan content**. The platform is not a payment processor, banking core system, identity-verification service, or customer-record system.

## 2. Data-handling inventory

| Data category | Product handling | Application-owned persistence | Retention expectation |
|---|---|---:|---|
| Raw submitted message, URL, email text, screenshot content | Processed in request memory to produce a verdict. Sensitive values are screened and redacted before eligible external analysis. | No application database or analytics archive is used for raw scans. | Request lifetime only. |
| OTPs, passwords, bank-account/card-like values, Aadhaar-like values | Privacy controls detect and remove/limit external analysis of sensitive content. | Not intentionally persisted by VerifyPulse. | Request lifetime only. |
| Local user feedback | Browser stores only result metadata, evidence labels, outcome choice, and timestamp. It excludes raw scan text, URLs, OTPs, numbers, and bank details. | User device only (`localStorage`), controlled by the user. | Until the user clears browser storage or exports/deletes it. |
| B2B audit events | Structured metadata only: correlation ID, key ID, tenant ID, outcome, status, scope, and error code. | Application emits to host/platform logs; no application-owned central log archive currently exists. | Hosting owner must configure and document the platform retention period before a regulated pilot. |
| Threat-intelligence indicators | Public indicators, source labels, confidence, and expiry metadata. | Versioned repository snapshot. No victim messages or customer identity data. | Expiry-bounded; regenerated by pipeline. |
| B2B API credentials | Only SHA-256 hashes in deployment configuration. Raw keys must stay in an approved secret manager/password manager. | Environment configuration only. | Until expiry, rotation, or revocation. |

## 3. Retention and deletion rules

1. VerifyPulse must not add raw scan logging, browser analytics replay, or message-content datasets without a documented purpose, data-flow review, user notice, and explicit approval.
2. The deployment owner must configure hosting/application logs so that access is restricted and retention is documented. Logs must not intentionally include raw scan content, URLs, credentials, contact information, IP addresses, or payment identifiers.
3. A B2B tenant API key must have a tenant ID, key ID, least-privilege scopes, expiry timestamp, and documented owner when the scoped key registry is used. A compromised key must be revoked by changing its status to `revoked` or removing it from the registry and redeploying.
4. User-device feedback is local-only. The UI provides export; deletion is controlled by clearing site data in the browser. VerifyPulse must not silently upload feedback.
5. If VerifyPulse begins storing any personal data, the owner must update this standard, publish an appropriate privacy notice, define a deletion/rights workflow, complete vendor review, and obtain legal review before enabling collection.

## 4. External provider and vendor boundaries

The scanner can use configured AI providers for eligible analysis. Before a bank/fintech pilot, the deployment owner must maintain a current vendor register identifying each provider, data category, purpose, region/processing terms where available, contract/DPA status, incident contact, and fallback behaviour.

No raw OTP, password, banking credential, or similar sensitive value should be sent to an external provider. The privacy guard is a defense-in-depth control, not a substitute for customer data-classification or contractual review.

## 5. Data-subject and enterprise requests

Because VerifyPulse does not operate an application-owned raw-scan database, there is ordinarily no raw scan record to retrieve or delete. For an enterprise pilot, the designated contact must respond to privacy/retention requests, confirm the applicable tenant configuration, and coordinate with the hosting provider only where platform-level logs or a separately enabled customer integration are involved.

## 7. Review cadence

Review this standard before every bank/fintech pilot, whenever a new provider or persistent datastore is introduced, and at least annually. Material changes require a privacy and security review before release.
